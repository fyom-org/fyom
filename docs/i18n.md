# Internationalization (i18n)

This document describes fyom's internationalization architecture, conventions,
and contributor workflow. It is the canonical reference for anyone adding
user-facing strings, locales, or backend error codes.

> **Status:** Phase 0 (infrastructure scaffold) shipped. Phases 1–5 are
> tracked in [`../ROADMAP.md`](../ROADMAP.md) section 9.9.

---

## 1. Goal

Ship a fully bilingual (English + Simplified Chinese) UI without regressing
the existing English-only behavior, and lay the groundwork for additional
locales without further architectural changes.

## 2. Supported Locales

| Code | Display Name      | Source? | Notes                                  |
|------|-------------------|---------|----------------------------------------|
| `en` | English           | Yes     | Source locale. Missing keys fall back here. |
| `zh` | 简体中文           | No      | Simplified Chinese.                    |

Adding a new locale (e.g. `ja`, `fr`) requires:

1. Drop a new `web/src/locales/<code>.json` file that mirrors `en.json` keys.
2. Append the code to `SUPPORTED_LOCALES` in
   [`web/src/plugins/i18n.ts`](../web/src/plugins/i18n.ts).
3. Add a label entry under the `language` namespace in **every** existing
   locale file so the selector can render the new locale's name in every
   language.
4. (Phase 4+) Update backend `supported_locales` validation list.

## 3. Locale Resolution Chain

### Anonymous users (Phase 0 — current)

```
navigator.language  →  DEFAULT_LOCALE ('en')
```

- Detected from `navigator.languages` (longest-prefix match against
  `SUPPORTED_LOCALES`).
- **Not persisted.** No `localStorage` write. The browser hint is re-read on
  every page load. This is a deliberate decision: persisting an anonymous
  locale would shadow the admin-managed `system_settings.default_locale`
  after a future login.

### Authenticated users (Phase 1 — planned)

```
users.preferred_language  →  system_settings.default_locale
                          →  navigator.language
                          →  'en'
```

- `users.preferred_language` is the highest-priority signal. Set explicitly
  via the Profile page language selector and persisted in the database.
- `system_settings.default_locale` is admin-managed via the admin Settings
  page "System Default Language" dropdown.
- `navigator.language` is the final fallback for users who never set a
  preference and whose admin never configured a default.

## 4. Architecture

```
Frontend (vue-i18n v9)              Backend (error_code layer — Phase 3)
┌─────────────────────────────┐     ┌──────────────────────────────────┐
│ web/src/locales/en.json     │     │ Response envelope:               │
│ web/src/locales/zh.json     │     │   { code: <http>,                │
│                             │     │     error_code: "auth.token",    │
│ $t('namespace.key')         │◄────│     message: "english text" }    │
│ t('namespace.key', params)  │     │                                  │
│                             │     │ pkg/errors/codes.go              │
│ Intl.DateTimeFormat         │     │   (stable error code constants)  │
│ Intl.NumberFormat           │     └──────────────────────────────────┘
└─────────────────────────────┘                  ▲
         ▲                                       │ Accept-Language header
         │ user.preferred_language (Phase 1)     │ (forward-compat signal;
         │ system_settings.default_locale (P1)   │  backend does NOT translate
         │ navigator.language                     │  message text today)
         └───────────────────────────────────────┘
```

**Key principle:** The backend does **not** translate messages. It emits a
stable `error_code` field; the frontend maps
`error_code → t('api_error.<code>')`. The existing `message` field is
retained for logs and as an English fallback.

## 5. File Layout

| Path                                   | Purpose                                      |
|----------------------------------------|----------------------------------------------|
| `web/src/locales/en.json`              | English strings (source of truth)            |
| `web/src/locales/zh.json`              | Simplified Chinese strings                    |
| `web/src/plugins/i18n.ts`              | vue-i18n instance creation + SUPPORTED_LOCALES |
| `web/src/composables/useLocale.ts`     | Detection, switching, `getCurrentLocale()`   |
| `web/src/main.ts`                      | Wires `app.use(i18n)` + `applyInitialLocale()` |
| `web/src/api/request.ts`               | Axios interceptor: `Accept-Language` header  |
| `docs/i18n.md`                         | This document                                |

## 6. Namespace Conventions

Locale JSON files use a flat namespace structure mirroring the view layer.
Every key MUST belong to a namespace; bare top-level keys are not allowed.

| Namespace    | Used By                              | Examples                              |
|--------------|--------------------------------------|---------------------------------------|
| `common`     | Reused across all views              | `save`, `cancel`, `loading`, `noData` |
| `nav`        | Top nav, side nav, route titles      | `home`, `dashboard`, `logout`         |
| `language`   | Language selector components         | `label`, `en`, `zh`, `systemDefault`  |
| `auth`       | Login, Register, password change     | `signIn`, `password`, `forgotPassword`|
| `dashboard`  | HomeView, DashboardView              | `welcome`, `recentlyAdded`            |
| `library`    | LibraryView, MediaDetailView         | `library`, `play`, `addToFavorites`   |
| `player`     | PlayerView                           | `play`, `pause`, `subtitles`          |
| `profile`    | ProfileView                          | `profile`, `changePassword`           |
| `admin`      | All `views/admin/*`                  | `users`, `libraries`, `permissions`   |
| `errors`     | Generic error toasts / fallbacks     | `generic`, `network`, `forbidden`     |
| `api_error`  | Backend error_code → message map     | `auth.token_invalid`, `media.not_found` |
| `validation` | Form field validators                | `required`, `minLength`, `email`      |

### Key Naming Rules

- **camelCase** for individual keys: `forgotPassword`, not `forgot_password`.
- **Dot-path navigation** in templates: `{{ $t('nav.dashboard') }}`.
- **Parameter interpolation** with named placeholders:
  `t('validation.minLength', { min: 8 })` → `"Must be at least 8 characters."`
- **Plurals** via vue-i18n's `plural` rule (Phase 2 will introduce as needed):
  ```json
  "items": "no items | one item | {count} items"
  ```

## 7. Contributor Workflow

### Adding a new user-facing string

1. **Pick the right namespace.** If the string is reused across views, it
   belongs in `common`. Otherwise it belongs to the view's namespace.
2. **Add the key to `en.json` first** (English is the source of truth).
3. **Add the same key to `zh.json`** with the Chinese translation. If you
   don't know the translation, leave the English string in place — the
   fallback chain handles it. Add a `// TODO: translate` comment in the PR.
4. **Use the key in the component:**
   ```vue
   <template>
     <button>{{ $t('common.save') }}</button>
   </template>
   <script setup lang="ts">
   import { useI18n } from 'vue-i18n';
   const { t } = useI18n();
   const message = t('errors.generic');
   </script>
   ```
5. **Never** hardcode English in templates or `alert()` calls. The lint rule
   (Phase 2) will catch these.

### Replacing `alert()` / `confirm()`

Phase 2 will replace all `alert()` / `confirm()` calls with Vue components
(`Toast`, `ConfirmDialog`). Until then, new code should NOT add new
`alert()`/`confirm()` calls — use the existing patterns or wait for Phase 2.

### Replacing `getApiErrorMessage(error)`

The current `getApiErrorMessage` helper (copy-pasted across 6 files) shows
the raw backend `message` to users. Phase 2 will replace it with a unified
`getApiErrorI18nKey(error)` that returns an `api_error.*` key. Until then,
new code should call `getApiErrorMessage` but plan to migrate.

## 8. Locale Switching (Hot-Swap)

Locale changes are **reactive**. Switching the locale does NOT require a
page refresh.

```ts
import { useLocale } from '@/composables/useLocale';

const { currentLocale, setLocale, supportedLocales } = useLocale();

// In an event handler:
setLocale('zh');
// All {{ $t(...) }} bindings re-render immediately.
```

Under the hood, `setLocale` mutates `i18n.global.locale.value` (a Vue ref).
vue-i18n's reactivity propagates to every `t()` / `$t()` consumer.

Side effects of `setLocale`:
- `<html lang="...">` attribute updates (for screen readers, search engines).
- `Accept-Language` header on subsequent axios requests (read at request
  time, not at module load — see
  [`request.ts`](../web/src/api/request.ts)).

## 9. Non-Goals

The following are **explicitly out of scope** for v1. They are documented
here to prevent scope creep and to give future contributors a clear "no"
when these requests arise.

### 9.1 Media Metadata Translation

**Decision:** NFO-imported titles, overviews, plots, actor names, genres,
and all other media metadata remain in their **source language**.

**Rationale:**
- NFO files are the canonical source. Translating them in-app would create
  a divergence between the filesystem and the database.
- Third-party scrapers (TMDB, TVDB) already provide localized metadata; if
  localization is desired, users should configure their scraper to fetch
  the desired language at import time.
- Translating metadata in-app would require a translations table, a UI for
  managing translations per-item, and a fallback chain per-field —
  significant complexity for a niche feature.

**Affected columns:** `media_items.title`, `media_items.overview`,
`media_items.plot`, `media_items.actors` (JSON), `media_items.genres`
(JSON), `media_items.directors`, `media_items.writers`, `media_items.studios`,
and all other NFO-derived fields.

**Future consideration:** If demand materializes, a separate
`media_item_translations` table keyed by `(media_item_id, locale)` could be
introduced. This would NOT change the source-of-truth `media_items` row.

### 9.2 CLI Banner / stderr Translation

**Decision:** The Go binary's CLI banner, log output, and stderr messages
remain in **English**.

**Rationale:**
- CLI output is operator-facing, not end-user-facing. Operators need to
  grep logs, share stack traces, and paste errors into search engines.
- Translating log output would break log-grepping pipelines and
  third-party monitoring tools that pattern-match on English strings.
- The CLI banner is a brand element; consistency across locales matters
  more than translation.

**Affected surfaces:** `cmd/fyom/main.go` banner, `internal/server` startup
logs, all `log.Printf` / `log.Error` calls, panic messages, signal-handler
output.

### 9.3 RTL (Right-to-Left) Layouts

**Decision:** Full RTL support (Arabic, Hebrew) is **not** in scope for v1.

**Rationale:**
- No current user demand for Arabic or Hebrew.
- RTL requires a complete CSS audit (every `margin-left` → `margin-inline-start`,
  every `text-align: left` → `text-align: start`, etc.).
- The visual QA cost is high without native RTL speakers on the team.

**Forward-compatibility rule:** All **new** CSS must use **logical properties**
(`padding-inline-start`, `margin-inline-end`, `text-align: start`,
`border-inline-start`) instead of physical ones (`padding-left`, etc.).
This keeps the RTL door open without requiring a future rewrite. Existing
physical-property CSS is grandfathered; do not refactor unless touching the
line for another reason.

### 9.4 Backend Message Translation

**Decision:** The backend does **not** translate `message` fields in API
responses.

**Rationale:**
- Backend messages are written for operators (logs) and as English
  fallbacks for the frontend.
- Translating them server-side would couple the backend to a translation
  library, require locale-aware caching, and duplicate the frontend's
  translation work.
- The `error_code` field (Phase 3) is the stable, locale-independent
  contract. The frontend translates `error_code` → user-facing string.

**Exception:** Backend may use `Accept-Language` for **logging** purposes
(e.g. logging the user's preferred locale alongside an error for
operator analysis). This is a future enhancement, not a current feature.

### 9.5 Timezone / Date Format Translation

**Decision:** fyom does **not** translate dates, times, or numbers via
vue-i18n. Use the native `Intl.DateTimeFormat` and `Intl.NumberFormat`
APIs instead.

**Rationale:**
- `Intl.*` is built into the browser, has no bundle-size cost, and supports
  far more locales than we ship JSON for.
- vue-i18n's datetime/number formatting is a thin wrapper over `Intl.*`
  anyway; using `Intl.*` directly is simpler and avoids coupling date
  formats to the locale JSON.

**Convention:**
```ts
// Good: use Intl directly
new Intl.DateTimeFormat(getCurrentLocale(), {
  year: 'numeric', month: 'short', day: 'numeric',
}).format(new Date(timestamp));

// Bad: don't put date formats in locale JSON
{ "dateFormat": "YYYY-MM-DD" }  // ❌
```

## 10. Testing

### Unit Tests

- `useLocale.ts` exports pure functions (`matchBrowserLanguageTag`,
  `detectBrowserLocale`) that are testable without a Vue component context.
- Tests should cover: exact match, prefix match, no match, empty
  `navigator.languages`, SSR (no `navigator`).

### Integration Tests

- Vue components that use `$t()` should render correctly with the default
  English locale.
- Locale switching mid-test should re-render without page refresh.
- Missing keys should fall back to English silently (no console error
  thanks to `missingWarn: false`).

### E2E Tests

- Existing Playwright tests should continue to pass with English locale.
- A future test should assert the Chinese locale renders Chinese strings
  for at least one view (Phase 2 deliverable).

## 11. Migration Checklist (Phase 2)

When extracting existing hardcoded strings:

- [ ] Run `rg "['\"][A-Z][a-z]+" web/src/views/` to find capitalized
      string literals (likely user-facing).
- [ ] For each file, group strings by namespace and add to `en.json`.
- [ ] Add Chinese translations to `zh.json` (or leave English with a
      `// TODO: translate` comment).
- [ ] Replace string literals with `$t('namespace.key')` or `t(...)`.
- [ ] Replace `alert(msg)` with the new Toast component (Phase 2 deliverable).
- [ ] Replace `confirm(msg)` with the new ConfirmDialog component.
- [ ] Replace `getApiErrorMessage(error)` calls with `t('api_error.' + getApiErrorCode(error))`
      (Phase 3 deliverable — until then, keep `getApiErrorMessage`).
- [ ] Run `pnpm run lint` and `pnpm run build` to verify no regressions.
- [ ] Manually switch locale in the UI to verify hot-swap works.

## 12. Glossary

- **Locale** — A language+region identifier (e.g. `en-US`, `zh-CN`). fyom
  uses language-only codes (`en`, `zh`) for simplicity.
- **Source locale** — The locale whose JSON file is the canonical source
  of strings. English (`en`) is fyom's source locale.
- **Fallback locale** — The locale used when a key is missing in the
  active locale. Always `en` in fyom.
- **`error_code`** — A stable, dot-separated string emitted by the backend
  (Phase 3) that the frontend maps to a translated string. Example:
  `auth.token_invalid`, `media.not_found`.
- **Hot-swap** — Changing the active locale without a page refresh, via
  vue-i18n's reactive `locale.value` reassignment.
